# 需求与可复制阶段提示

本轮目标：同一虚构会员/课程/预约记录贯穿预约、管理查看、重复提交、取消和重开。第一版不做支付、身份认证、营销、核销或生产部署。运行入口为 app.py，界面为 index.html，数据库为 data/booking.sqlite3，统计样本为 fixtures/report.json。

以下用于理解、复演或自己的新练习，不是当时逐字输入的伪造开发聊天，也不保证任何工具一次生成完全一样的代码。实际开发与修复证据另随录制资料保存。

## 1. 先厘清需求

> 做一个拳馆预约教学小样，只用虚构数据。先不要写代码。按使用者、动作、数据、操作后的变化、失败提示整理需求，列出影响实现但尚未确认的问题。第一版只做查看课程、预约、管理查看、取消，不自行增加支付、营销、核销和正式身份系统。

确认：课时3、已用0；预约先预留1而不是已用1；同一有效预约重复提交不新增；取消释放预留和课程名额；状态保存在服务端本机SQLite；演示角色不是权限隔离。

## 2. 计划、运行条件与实施

> 根据这份需求，先列计划及每步检查结果，再实施。使用Python标准库SQLite和HTTP服务、普通HTML，不安装额外依赖，只监听127.0.0.1。告诉我启动、停止、重置方法、数据位置及未验证范围。不要接入客户或生产数据。

## 3. 实际操作反馈

> 我做了【实际动作】，预期【约定结果】，实际得到【观察结果】。相关预约编号是【当次编号】。先定位原因，说明最小改动，保留已确认规则；修完复走受影响流程，不用“已完成”代替真实检查。

## 4. 修改前保存

> 先保存当前可运行版本，说明哪些已通过、哪些还没有验证，再做本轮具体修改。代码存档不等于业务数据备份。修改后回归受影响流程，再保存新版本。

本轮真实问题：首个模型报告把统计结束日期写得含糊。修复前已有本地Git基线；随后明确9/8不含、9/7全天包含，并进行真实复测。不是故意制造的错误。

## 5. 经营统计与模型解释

> 先按固定期间从虚构记录计算完成、取消、活跃覆盖、卖课收款，给出记录ID供人工核对。确定统计正确后，再把汇总和我的问题交给模型。正文用自然经营语言，依据单独显示；没有成本不能算利润，没有同批追踪不能说留存提升。失败显示真实状态，不自动切离线答案。

实际模型问题建议：先问“这周的上课、取消和卖课收款情况怎么样？”，再问“这周赚了多少利润？留存是不是提高了？”每次实时请求会使用自己的模型额度。
